## 2. 旧接口保持与新增输出

原有两个主要话题及消息结构保留，不要求规划方换成新的点云接口。

| 话题 | 类型 | 内容/坐标系 |
| --- | --- | --- |
| `/T3/semantic/current_pose` | `nav_msgs/msg/Odometry` | `odom → base_link` 当前视觉定位 |
| `/T3/semantic/incremental_map` | `t3_interfaces/msg/IncrementalSemanticMap` | 64×64 m 滚动矩形窗口；坐标以消息 `header` 和 `origin` 为准 |
| `/T3/semantic/trajectory` | `nav_msgs/msg/Path` | `map` 下的轨迹 |
| `/T3/mapping/grid_map` | `grid_map_msgs/msg/GridMap` | 当前局部高程栅格，当前配置为 `odom` |
| `/T3/mapping/global_grid_map` | `grid_map_msgs/msg/GridMap` | `map` 下的完整全局高程栅格，低频更新 |
| `/T3/mapping/global_overview` | `nav_msgs/msg/OccupancyGrid` | 低分辨率全局概览，不是完整规划代价地图 |
| `/T3/mapping/lidar_map` | `sensor_msgs/msg/PointCloud2` | `map` 下的三维点云预览，最多 20 万点 |
| `/T3/mapping/lidar_incremental` | `sensor_msgs/msg/PointCloud2` | 视觉配准后的新观测帧，可能含已观察过的点 |
| `/T3/mapping/lidar_status` | `std_msgs/msg/String` | 点云体素数、文件路径等 JSON 状态 |

兼容位姿别名 `/Car/T3/localization/odometry` 保留。
`map` 与 `odom` 的关系通过 TF 提供，不要仅因为数值接近就当成同一坐标系。
`/car/pose`、`/car/odom` 是仿真通信节点的参考数据，其原点可能与算法不同，不能直接替代课题三位姿。

订阅 QoS：位姿 `RELIABLE / VOLATILE / depth=10`；轨迹、栅格和当前滚动增量地图 `RELIABLE / TRANSIENT_LOCAL / depth=1`。
LiDAR 新观测 `RELIABLE / VOLATILE / depth=5`，累计预览 `RELIABLE / TRANSIENT_LOCAL / depth=1`。

增量地图保持旧结构：`header, update_id, resolution, width, height, origin` 加各层数组。
数组为行优先 `index=row*width+column`；`origin` 是左下角位置；米为长度单位。
`occupancy` 为 -1 未知、0～100 占据概率百分数，0/100 是自由/占据两个端点，不能只按三值解析；未观测高程等浮点值为 NaN。
滚动模式的每个消息是完整矩形窗口，不应误当成仅含差分格子的补丁。

当前未启用课题二语义 mask，不能把占位语义当成已验证分类结果。
高程、粗糙度与占据字段不自动等于经过足迹、坡度、台阶等约束验证的可通行代价；规划方需按自己的要求适配。
LiDAR 辅助分支主要扩展高程证据，并不把所有新高程格自动标成自由空间；有高程、占据未知是合法状态。

ROS 车体轴为前/左/上（FLU），相机光学轴为右/下/前；原标定表车体轴为前/右/下，启动文件中做了转换。
左相机在 ROS 车体中的平移约 `(0.529842, 0.129759, 0.831680) m`；LiDAR 约 `(0.606528, -0.002300, 0.612013) m`。
完整旋转矩阵以 YAML 为准，不只凭这三个平移量配置传感器。

点云变换为 `p_map = T_map_base × T_base_lidar × p_lidar`；`T_map_base` 来自视觉定位。
Env_X 输入已经是 ROS FLU，而原测量外参的雷达轴是 FRD。演示配置现对外参两端转换：`T_base_input = D × T_measured × D`，`D=diag(1,-1,-1,1)`；只左乘 D 会把地面翻到车体上方。
原 LiDAR 数据厘米到米的换算在数采端完成，不要再乘一次 0.01。
如果 UE 场景更换了相机位置、方向、FOV 或 LiDAR 安装方式，必须重新核对这些参数；旧配置不能证明当前 UE actor 的几何必然一致。
每次自动录包会复制两份 YAML 并导出实际节点参数，以便后续复现实验。

## 5. 内存、算力与磁盘边界

本机约 61 GiB RAM。实测单套视觉定位进程 RSS 约 8 GiB；多进程共享页与 GPU 统一内存不能简单重复相加。
此前系统约 14 GiB 已用、46 GiB 可用时，另有一套 Point-LIO 约 2.8 GiB；这不属于内存耗尽。

当前策略：

- 双目队列有长度限制；数采默认最高 0.25 Hz，P3 数采只发布本流程需要的双目和 LiDAR。
- 关键帧 RGB 原图仅保留最近 8 帧，历史位姿、特征和三维几何仍保留；当前追踪缓存独立。默认通用算法仍保留原行为，只有本演示配置开启此限制。
- 完整 LiDAR 体素存 SQLite；三维预览最多 20 万点；PCD 分块写出，不一次加载整张点云。
- 局部输出保持 64×64 m；观测内存缓存 32 条；轨迹显示最多 5000 点，完整轨迹文件另存。
- 全局稠密地图最短 10 秒重新构建/发布一次；局部栅格和旧增量接口不受这个低频限制。
- 地图持久化编码工作线程 2 个，PCD 导出 1 个；录包低优先级，缓存 128 MiB（双缓冲最坏约 256 MiB）。
- 自动路线保留至少 8 GiB 系统可用内存、10 GiB 磁盘；低于阈值停车并收尾录包，不结束别人的进程。
- 历史回放也检测上述资源余量，异常时停止继续送帧并保存已有地图。手动实时建图没有因此变成硬内存配额，需查看状态和适时停止。

**仍有边界：** 全局栅格块、视觉关键帧和视觉地图点仍随历史增长，当前不是所有状态都已做磁盘换页/LRU 的严格常量内存方案。
低频发布降低重复构建和传输开销，但不能消除完整稠密地图的一次性分配。长于已验证时长、很大空间跨度或高频输入，需要依据资源记录重新评估，不承诺无限时长无增长。

系统盘检查时剩余约 121 GiB。主要占用是历史 bag：`Env_X/InterFace/bags/20260825_232412` 约 1.50 TB，另一个约 90 GB；不是这套代码占了大头。
长路线启动前按 30 MB/s 的保守录制预算检查剩余空间；实际录制大小以本次 bag 为准。不自动删除历史数据来腾空间。
