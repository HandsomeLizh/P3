# 课题三定位与 2.5D 栅格地图使用与接口说明

> 适用工程：`t3_gridmap_v2_ws`  
> 目标环境：ROS 2 Humble + Cyclone DDS；本机 ROS 2 Rolling 已完成兼容构建  
> 文档更新：2026-08-15

## 1. 当前设计结论

本节点完成可选 VO/LIO 定位，并将立体点或 `PointCloud2` 点、语义标签和
占据信息融合为多层 2.5D 栅格地图。

当前采用“内外分离”设计：

- 内部全局地图使用稀疏瓦片，机器人离开初始 60 m 区域后仍可继续建图。
- 旧 ROS 2 话题和 `IncrementalSemanticMap.msg` 消息定义保持不变；
  显式 `full_tiles` 另有小型批次元数据话题。
- 默认使用 `fixed`，完全保留原始的固定 60 m 地图输出语义。
- 定位默认仍为 `vo + none`，因此原有 RoMa 功能和接口不变。
- 新增 `lio + none` 直接 LIO 与 `vo_lio + gtsam_gp` 局部因子图融合，均为显式开关。
- 地图几何默认来自双目；可选 `direct` 直接点云建图，也可选
  `assist` 用时间对齐的点云校正双目远距离深度。“位姿来源”和
  “地图几何来源”是两组独立开关。
- 当且仅当使用 `lio + direct` 且明确关闭双目回退时，位姿和地图几何都不再
  消费视觉结果，因此不加载或运行 RoMa；同步图像和语义图仍用于给点云投影语义。
- `direct` 将语义类别与几何占据分开：可靠地面终点提供 free，可靠非地面
  终点提供 occupied，无法可靠判断的终点保持 unknown；明确的图像语义优先。
- FAST-LIO2 作为独立 ROS 2 进程，课题三只消费标准
  `nav_msgs/msg/Odometry`，便于以后替换 LIO 实现。
- 额外保留 `rolling_window` 和 `full_tiles` 两种可选方案，但必须在与接收方
  确认处理规则后再启用。

```text
左/右相机 + IMU ──► RoMa VO ──┐
                                      ├──► 定位选择器 ──► 位姿、轨迹、TF
原始 LiDAR + IMU ──► FAST-LIO2 ──► /Odometry ─┘       vo / lio / vo_lio
                                                               │
                 默认双目 3D 点 ─────────────────────┐
原始 PointCloud2 ── 可选 LiDAR 3D 点 ─────────────────┤
课题二语义标签 ──────────────────────────────────────────┘
                                                               │
                                                               ▼
                                                    语义/高程/占据融合
                 │
                 ▼
       稀疏瓦片全局 2.5D 地图
                 │
       ┌─────────┴─────────┐
       ▼                   ▼
  GridMap 等标准输出    IncrementalSemanticMap
                                  └─ full_tiles: SemanticMapBatch
```

图中的可选 `PointCloud2` 实际有两种用法：`direct` 用整帧点云替代双目地图几何，
`assist` 只将点云深度投影到受支持的双目像素射线上。两者都不改变定位模式或
对外输出类型；只有 `direct` 会额外生成局部表面的几何终点占据状态。

## 2. 工程结构

| 路径 | 作用 |
|---|---|
| `src/t1_dataset_sim` | 将数据集模拟成立体图像、可选 IMU、原始 LiDAR 和保存 LIO ROS 2 话题 |
| `src/t2_basic_semantics` | 联调用基础语义分割，不是最终课题二模型 |
| `src/t3_interfaces` | `IncrementalSemanticMap` 载荷与 `SemanticMapBatch` 批次元数据 |
| `src/t3_semantic_mapping` | RoMa 定位、2.5D 融合、ROS 2 发布与快照 |
| `src/t3_semantic_mapping/.../input_transport.py` | 输入 QoS、时间同步和左右目偏差保护 |
| `src/t3_semantic_mapping/.../localization` | 外部里程计适配、时间缓冲、定位路由和可选 GTSAM 因子图 |
| `src/t3_semantic_mapping/.../lidar_occupancy.py` | `direct` 点云局部地面/非地面终点判断，不改变语义标签 |
| `src/t3_semantic_mapping/.../snapshot_store.py` | 版本化快照、fsync、根索引原子提交、上一版保留与受限清理 |
| `src/grid_map_msgs` | 标准 `grid_map_msgs` 2.4.0 接口的随工程副本，消息类型不变 |
| `scripts` | 环境、编译、数据回放、监视、RViz 和测试脚本 |
| `ARCHITECTURE.md` | 简要架构说明 |
| `课题三ROS2输入接口联调说明.md` | 正式输入缺口、配置方法和联调清单 |

执行 `source scripts/enter_workspace.sh` 后，环境会把工作空间内置的
`third_party/RoMa/` 设为 `T3_ALGORITHM_ROOT`，三个 launch 均使用这个统一默认值。
显式 `algorithm_root:=...` 仍具有最高优先级，但正常部署不需要指向工作空间之外。
`data_dir` 和 `output_dir` 同样可分别用 `T3_DATA_DIR`、`T3_OUTPUT_DIR`
设置新机器默认路径；显式 launch 参数仍优先，原默认回退保留。

已编译验证的 FAST-LIO2 ROS 2 候选位于工作空间内的隔离第三方目录
`third_party/fastlio2/src/FAST_LIO_ROS2`，固定提交为
`2fffc570a25d0df172720bac034fbdb6a13d2162`。它是
[`Ericsii/FAST_LIO_ROS2`](https://github.com/Ericsii/FAST_LIO_ROS2) 社区移植，
不是独立的官方原生 ROS 2 重写。需要特别说明：
[`hku-mars/FAST_LIO`](https://github.com/hku-mars/FAST_LIO/tree/ROS2) 官方组织仓库
现在确实也挂有 `ROS2` 分支（审核提交
`a4743b095409588842a5b30ddfa27e29d2f99164`），但该分支 README 自身标明
`ROS2 Fork repo maintainer: Ericsiii`，构建说明也指向 Ericsii 的仓库。因此准确说法是
“官方组织托管了社区移植分支”，而不是“没有官方仓库分支”。课题三不直接
修改任一上游。上游源码会随交付包保存在 `third_party/`，但不并入自研 `src/`。

## 3. 环境与编译

### 3.1 软件环境

- Ubuntu + ROS 2 Humble；当前机器同时验证了 ROS 2 Rolling
- Cyclone DDS：`rmw_cyclonedds_cpp`
- Python 虚拟环境默认：`~/venvs/ros2_roma_cv4`
- PyTorch + CUDA，用于 RoMa 匹配
- `grid_map_msgs`、`cv_bridge`、`message_filters`、`tf2_ros`
- `gtsam` 与 `gtsam_unstable`：仅 `vo_lio + gtsam_gp` 模式需要，默认 VO 不导入
- 社区 FAST-LIO ROS 2 另需 `pcl_ros`、`pcl_conversions`和
  `livox_ros_driver2`，由工程脚本在 `third_party/fastlio2` 的隔离构建目录中编译

### 3.2 首次安装和编译

```bash
cd /opt/t3_gridmap_v2_ws

bash scripts/install_prereqs.sh
bash scripts/build.sh
source scripts/enter_workspace.sh
bash scripts/check_environment.sh
```

`scripts/build.sh` 和 `scripts/enter_workspace.sh` 优先加载 Humble；机器未安装 Humble
时会使用现有 Rolling，也可用 `ROS_SETUP_FILE=/opt/ros/<发行版>/setup.bash` 显式指定。
如果显式设置 `ROS_VENV`，脚本会严格检查该环境；未设置且默认环境不存在时使用
ROS 对应的系统 Python。激活脚本可重复 source；运行包装脚本内部的再激活
不会把缺失的自动默认 venv 误判成用户显式错误。中文工作区下的中间构建目录
会自动移到 `/tmp`，安装结果
仍写入本工作区的 `install`。所有模式均设置 Cyclone DDS。

### 3.3 FAST-LIO2 的选用边界

当前选用社区 ROS 2 移植是因为它直接发布 `/Odometry`，且默认帧为
`camera_init -> body`，与本适配层的边界一致。该仓库根目录 `LICENSE` 为
GPL-2.0，但 `package.xml` 标成 BSD，存在不一致；在法务确认前应按更严格的
GPL-2.0 对待，并继续通过 ROS 2 进程边界隔离。

本地仓库还已将官方组织的 `ROS2` 分支添加为 `hku-mars/ROS2` remote 供对比。
它与当前 Ericsii 工作树已分叉；适配层不依赖两者的私有消息，仅依赖标准
`nav_msgs/msg/Odometry`，所以后续根据实车 LiDAR 型号和无修改编译结果切换时无需改
课题三代码。

本机 Ubuntu 20.04 + 旧 Rolling 已完成 `Livox-SDK2`、
`livox_ros_driver2` 和 `fast_lio` 无算法源码补丁的编译，并实际验证了
`/laser_mapping`、`/Odometry` 及 `/cloud_registered_body` 的 ROS 2 类型、
QoS 和动态链接。旧 Rolling 的 CMake/ament 兼容处理只位于外部工作区，
没有改动课题三默认 VO 功能。正式车载环境仍建议 Ubuntu 22.04 + ROS 2 Humble。
完整部署命令、锁定版本和验收清单见
[课题三新机器部署与FAST-LIO2编译说明.md](课题三新机器部署与FAST-LIO2编译说明.md)。

### 3.4 gnssFGO 参考边界

[`rwth-irt/gnssFGO`](https://github.com/rwth-irt/gnssFGO) 已克隆到
`/opt/reference/gnssFGO`，当前 `ros2` 分支提交为
`012b95296ac20b800ecb3c36e3c95229df05ae51`，本地分支为 `rwth-ros2` 并跟踪
`origin/ros2`；`origin` 已确认是 `rwth-irt` 官方地址。之前审核过的社区
ROS 2 fork 只保留为 `ros2-fork` remote，不是当前工作树。本工程参考其 WNOA
连续时间运动先验形式：

```text
Q(dt) = [[dt^3/3 Qc, dt^2/2 Qc],
         [dt^2/2 Qc, dt Qc]]
```

但没有把整个 gnssFGO 后端嵌入课题三。当前 `gtsam_gp` 只保留适合本项目的
`Pose3 + 6D body-tangent velocity`、鲁棒 VO/LIO 相对位姿因子和 fixed-lag 滑窗；
不包含 GNSS 因子、gnssFGO 完整插值器、全局回环或其他传感器插件。这样可以
让默认 VO 不依赖大型后端，也避免 FAST-LIO2 已使用的 IMU 被重复加入因子图。

## 4. 使用当前数据集测试

已用于联调的序列：

```text
/data/batch_organized/2025-06-26-20-21-08
```

### 4.1 在线生成基础语义

这种方式会同时启动数据发布、基础语义节点和课题三地图节点：

```bash
cd /opt/t3_gridmap_v2_ws
source scripts/enter_workspace.sh

bash scripts/run_batch_organized.sh \
  /data/batch_organized/2025-06-26-20-21-08 \
  max_frames:=3 \
  playback_rate:=1.0 \
  start_delay_sec:=0.0 \
  output_dir:=/tmp/t3_map_test
```

两个数据集联合 launch 现在默认 `lossless_playback=true`。
`start_delay_sec` 只是开始检查前的最短等待；即使设为 0，发布器也会等到
mapper 的左/右/语义三路订阅和 `/Car/T3/debug/input_processed`
publisher 真实出现。默认最多 2 帧图像在途，每帧获得单独回执后才释放窗口；
不合并、不抽帧。

回放完成后不要只看终端的“已播完”，应同时检查：

```bash
python3 -m json.tool /tmp/t3_map_test/dataset_playback_summary.json
python3 -m json.tool /tmp/t3_map_test/input_processing_summary.json
```

前者证明预期/发布/回执帧是否一致，后者区分有效位姿、跟踪失败、定位不可用、
处理异常和显式拒绝。一条回执只表示该回调已终止，不表示必然产生有效地图。

### 4.2 使用预生成语义

数据目录需包含 `semantic_labels` 子目录，且语义图文件名要与左图一致。

```bash
  data_dir:=/data/batch_organized/2025-06-26-20-21-08 \
  algorithm_root:=/opt/t3_gridmap_v2_ws/third_party/RoMa \

```

### 4.3 可选 PointCloud2 数据集回放

纯双目建图默认只融合相机光轴深度 `Z<=5 m` 的可信点：

```bash
bash scripts/run_batch_organized.sh \
  /data/batch_organized/2025-06-26-23-42-20 \
  enable_lidar_mapping:=false \
  stereo_map_max_depth_m:=5.0
```

该门限不删除定位端的远特征；无可信几何的远处地图格保持 `unknown`。
设为 `0.0` 可恢复旧的无上限观测，但只应用于已独立验证远距离深度的
新标定。若以后需要重算被拒绝的远点，必须保留原始左/右图或 rosbag；
SQLite 保存的是已接受的地图证据。

使用主评估序列的原始 `lidar_raw/*.pcd`。直接点云几何模式：

```bash
bash scripts/run_batch_organized.sh \
  /data/batch_organized/2025-06-26-23-42-20 \
  enable_lidar_mapping:=true \
  lidar_mapping_mode:=direct \
  lidar_temporal_mode:=none \
  lidar_publish_max_points:=5000 \
  max_frames:=10 \
  playback_rate:=0.2 \
  start_delay_sec:=0.0 \
  output_dir:=/tmp/t3_map_pointcloud_direct
```

点云辅助双目深度模式：

```bash
bash scripts/run_batch_organized.sh \
  /data/batch_organized/2025-06-26-23-42-20 \
  enable_lidar_mapping:=true \
  lidar_mapping_mode:=assist \
  lidar_temporal_mode:=none \
  lidar_publish_max_points:=20000 \
  pointcloud_assist_max_points_per_keyframe:=20000 \
  lidar_fallback_to_stereo:=true \
  max_frames:=10 \
  playback_rate:=0.2 \
  start_delay_sec:=0.0 \
  output_dir:=/tmp/t3_map_pointcloud_assist
```

`assist` 默认保留相机 Z 深度不超过 5 m 的双目点；只有当时间对齐点云在
2 px 半径内提供支持时，才用点云深度替换大于 5 m 的双目深度；没有点云支持的
远点不进入地图。它是稀疏关键帧地图深度修正，不是稠密补全，也不改 RoMa VO/PnP。

`lidar_publish_max_points` 只用于 Python 数据集模拟器降采样；设为 `0` 表示完整转发。
实车或 rosbag 原生 `PointCloud2` 不受它限制。`direct` 关键帧默认保留 5,000 点，
`assist` 为了获得更多像素支持默认保留 20,000 点。

上面两条是保留旧数据集对照的 `none` 模式，不做逐点或整帧运动修正，
不应作为高速精度验收配置。目标序列的已保存 LIO 回放请用第 4.4 节脚本；
实车请使用第 5.1/6.1 节的 FAST-LIO2 已去畸变点云路径。

`direct` 的未知语义点不会再统一当作“只有射线、没有终点证据”。点云变换到
最终 `map` 坐标后，节点用局部 k 近邻法向区分可靠地面和非地面：地面终点为
free，墙面、顶面和其他可靠非地面终点为 occupied；稀疏、单线或粗糙邻域仍为
unknown。相机已经明确给出的地面/障碍语义优先于几何判断。该逻辑不用于
`assist` 或纯双目。

关闭方式是 `enable_lidar_mapping:=false`。关闭后不创建点云订阅，executor、双目地图路径、
话题和消息类型均保持原行为。

### 4.4 目标序列的 LIO 接口回放

序列 `2025-06-26-23-01-34` 包含已保存的 FAST-LIO 估计轨迹。可用下列脚本
同时回放标准 `/Odometry`、原始点云、图像、IMU 和语义：

```bash
cd /opt/t3_gridmap_v2_ws
CUDA_VISIBLE_DEVICES=2 bash scripts/run_target_lio_replay.sh
```

该脚本专用于**确定性接口联调**，不是实车 LIO 运行方式：

- `lidar_fastlio/trajectory.npz` 是定位算法的已保存输出，**不是真值**，不能再拿来
  评价同一条 FAST-LIO 轨迹精度。
- 脚本内 `T_lidar_body` 由该录制的原始点云、配准点云和保存位姿刚体配准
  恢复，多帧交叉验证中 99.9% 以上点的残差小于 1 cm。它只保证该数据回放
  自洽，不能代替实车 IMU–LiDAR 外参标定。
- 正式 rosbag/实时系统要从原始 LiDAR + IMU 现场运行 FAST-LIO2，而不是
  发布这个 `.npz`。
- 脚本已显式使用 `lidar_temporal_mode=per_point`、`time`、`sec`；
  该序列原始点时间约为 `-0.10~+0.00064 s` 相对 `Header.stamp`。
  保存的约 10 Hz LIO 插值不等价于 FAST-LIO2 高频 IMU deskew，
  所以该模式只是可测的备选/接口回放。
- 目标序列左右目中位时差约 147 ms；脚本为接口联调放宽到 200 ms。这不能
  被解读为高精度双目 VO/深度结果。

## 5. rosbag 接入

rosbag 中应包含左图、右图、IMU 和语义标签图。LiDAR 定位/地图模式还应包含原始
`sensor_msgs/msg/PointCloud2`；如果 bag 已包含现场计算的 `/Odometry`，也可直接回放该话题。
建议先启动地图节点，等待
RoMa 模型加载完成后再播放 bag。

终端 1：

```bash
cd /opt/t3_gridmap_v2_ws
source scripts/enter_workspace.sh

bash scripts/run_bag_mapper.sh \
  data_dir:=/path/to/calibration_or_sequence \
  algorithm_root:=/opt/t3_gridmap_v2_ws/third_party/RoMa \
  output_dir:=/path/to/output \
  incremental_publish_mode:=fixed \
  enable_lidar_mapping:=true \
  lidar_mapping_mode:=assist \
  lidar_topic:=/Car/T1/fusion/lidar/points \
  lidar_extrinsics_path:=/path/to/extrinsics.json \
  lidar_expected_frame_id:=velodyne \
  lidar_fallback_to_stereo:=true
```

终端 2：

```bash
source /opt/ros/humble/setup.bash
export RMW_IMPLEMENTATION=rmw_cyclonedds_cpp
ros2 bag play /path/to/bag --clock
```

标准 `ros2 bag play` 目前不消费 T3 的逐帧回执，所以不具有第 4 节数据集
发布器的自动节流保证。先用保守的 `--rate`（例如根据当前 x86 实测使用
`--rate 0.2`），播放结束后继续等 mapper 处理完，并将 bag 中三图帧数与
`input_processing_summary.json` 的三路到达/同步/终止数对比。如果要与
数据集同等的自动保护，应实现独立的 ack-aware bag player，不应把 bag
解包/重放逻辑放进 mapper。

如果 bag 不包含语义标签，需要同时运行课题二节点，并向
`/Car/T2/semantic/label_image` 发布与左相机相同时间戳的标签图。

若不使用 LiDAR，保持 `enable_lidar_mapping:=false` 即可；其余接口和命令不变。

### 5.1 从原始 LiDAR + IMU 运行 FAST-LIO2（正式用法）

先启动工作空间内部隔离编译的 FAST-LIO2，社区移植的基本命令为：

```bash
source /opt/ros/humble/setup.bash
source /path/to/livox_ws/install/setup.bash
source /path/to/fastlio_ws/install/setup.bash
ros2 launch fast_lio mapping.launch.py config_file:=<your_sensor.yaml>
```

`<your_sensor.yaml>` 必须与实际 LiDAR 型号、点时间单位、扫描线数、LiDAR 和 IMU
话题一致。`mapping.extrinsic_T/R` 按该实现的约定表示“LiDAR 在 IMU
body 中的位姿”，即 `T_body_lidar`。已有可靠标定时建议
`extrinsic_est_en=false`。

再启动课题三 mapper：

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  data_dir:=/path/to/calibration \
  algorithm_root:=/opt/t3_gridmap_v2_ws/third_party/RoMa \
  output_dir:=/path/to/output \
  localization_mode:=lio \
  fusion_backend:=none \
  enable_imu:=false \
  lio_odometry_topic:=/Odometry \
  lio_expected_parent_frame:=camera_init \
  lio_expected_child_frame:=body \
  lio_child_to_lidar_transform:="[<16 row-major values>]" \
  lio_child_to_lidar_confirmed:=true \
  enable_lidar_mapping:=true \
  lidar_mapping_mode:=direct \
  lidar_fallback_to_stereo:=false \
  keyframe_interval:=5 \
  publish_layer_images:=false \
  publish_map_pointcloud:=false
```

上述四个模式条件 `localization_mode=lio`、`enable_lidar_mapping=true`、
`lidar_mapping_mode=direct`、`lidar_fallback_to_stereo=false` 同时成立时，节点
不会导入或逐帧运行 RoMa。`algorithm_root` 可为统一部署保留，但该组合不会访问其中
的模型代码。这里的 `enable_imu=false` 只关闭课题三 mapper 中给视觉前端使用的
IMU 订阅；上方独立 FAST-LIO2 进程仍按其配置订阅原始 IMU，并通过 `/Odometry`
提供已经融合的位姿。相机标定、左右图和语义图仍然需要：标定用于点云投影，三图同步回调
提供建图时刻及语义。有效 LIO 位姿计数为 1 或可被 `keyframe_interval` 整除时
取一次关键帧；无效 LIO 位姿不消耗节拍。要加密地图可把该值改为 1 或 2，
但需同时复测覆盖率、存储量和回调耗时。

这里必须传入 `T_lidar_child = inverse(T_body_lidar)`，不是直接把 FAST-LIO2
配置中的 `extrinsic_R/T` 原样复制。节点还会从相机标定读取
`T_camera_lidar`，最终使用：

```text
T_camera_child = T_camera_lidar * T_lidar_child
T_parent_camera = T_parent_child * inverse(T_camera_child)
```

未设置 `lio_child_to_lidar_confirmed:=true` 时，外部 LIO 模式会拒绝启动，避免把
IMU/body 位姿错当成 LiDAR 或相机位姿。

## 6. 实时 ROS 2 系统接入

实时系统中只启动 mapper，不启动数据集模拟节点：

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  use_sim_time:=false \
  data_dir:=/path/to/calibration_or_sequence \
  algorithm_root:=/opt/t3_gridmap_v2_ws/third_party/RoMa \
  output_dir:=/path/to/output \
  incremental_publish_mode:=fixed \
  enable_lidar_mapping:=true \
  lidar_mapping_mode:=assist \
  lidar_topic:=/Car/T1/fusion/lidar/points \
  lidar_extrinsics_path:=/path/to/extrinsics.json \
  lidar_expected_frame_id:=velodyne \
  lidar_fallback_to_stereo:=true
```

如果实时 FAST-LIO2 已在发布 `/Odometry`，在上述命令再加入第 5.1 节的
`localization_mode:=lio`、帧名和已确认外参即可。需要 VO/LIO 融合时改为：

```text
localization_mode:=vo_lio fusion_backend:=gtsam_gp
```

`vo_lio` 是局部 fixed-lag 融合。外部定位模式仍必须保持 RoMa 内部的
`enable_backend=false` 与 `enable_loop_closing=false`，避免让冻结视觉后端与外部轨迹
同时拥有全局修正。需要全局闭环时，可另行显式开启已经隔离实现的
`enable_global_loop_closure:=true`：MPRF/Scan Context 只提供候选，候选必须通过
本进程 LiDAR ICP 与时序确认后才进入独立 iSAM2，修正不回灌局部估计器。
完整算法、部署和真实序列结果见
`课题三MPRF闭环实现与部署说明.md`。

当前 mapper 直接从标定文件读取内参和基线，并不订阅 `CameraInfo`。

### 6.1 实时输入要求

| 话题 | 类型 | 默认帧 | 内容要求 |
|---|---|---|---|
| `/Car/T1/fusion/stereo/left/image_raw` | `sensor_msgs/msg/Image` | `car_stereo_left_optical_frame` | BGR8 左目图像 |
| `/Car/T1/fusion/stereo/right/image_raw` | `sensor_msgs/msg/Image` | `car_stereo_right_optical_frame` | BGR8 右目图像 |
| `/Car/T1/fusion/imu/data` | `sensor_msgs/msg/Imu` | `car_imu_body_frame` | 角速度单位 rad/s |
| `/Car/T2/semantic/label_image` | `sensor_msgs/msg/Image` | 与左图一致 | `mono8`，每像素为语义 ID |
| `/Car/T1/fusion/lidar/points`（可选） | `sensor_msgs/msg/PointCloud2` | `velodyne`（可配置） | 至少包含标量 `x/y/z`，支持 float32/float64 |
| `/Odometry`（`lio` / `vo_lio`） | `nav_msgs/msg/Odometry` | `camera_init -> body` | FAST-LIO2 外部位姿，必须使用原始传感器时间 |

默认仍使用严格 `TimeSynchronizer`，三者 `Header.stamp` 必须完全相同。
已确认上游存在小量时间戳偏差时，可显式改为 `approximate`；与此同时，
左右目仍由独立的 `stereo_sync_max_skew_sec=0` 精度门限保护，不会因为
等待语义图就默认放宽双目采集偏差。IMU 使用独立时间缓冲区，按图像
时间戳积分。

双目、语义和 IMU 的 Reliability 可分别匹配实际发布端，图像与 IMU 的
DDS depth 也分开配置。不要在没查 `ros2 topic info --verbose` 的情况下
把所有输入盲目改为 Best Effort；大图像分片丢失会使整帧失效。完整的选择方法、
诊断日志和课题一/二待提供材料见
[《课题三 ROS 2 输入接口联调说明》](课题三ROS2输入接口联调说明.md)。

实时 mapper 也会发布 `/Car/T3/debug/input_processed` 并在正常关闭时写
`input_processing_summary.json`，但它只能证明已经进入同步回调的帧有了结果。
它不会操作课题一驱动降速，也无法恢复 DDS 之前已经丢失的历史帧。
上车必须同时获取课题一发布序号/计数，并验证 T3 在长时稳态下的真实处理频率。

点云不进入上述三图精确同步器。开启后，节点等待有序点云流到达/越过
图像时刻，再在前驱和后继中选择真正时间最近且绝对时差不超过 0.15 s
的点云，并校验 `frame_id`。这比修改前“一旦有过去帧进入门限就立即返回”更准确，
正常最多增加约一个点云周期的配对延迟。接收线程最多额外等待 1 s 让
已在传输中的点云到达，但不会放宽传感器时间门限。无匹配点云时默认只跳过该关键帧
的地图观测，定位仍继续。显式设置 `lidar_fallback_to_stereo:=true` 时，`direct`
会退回到与纯双目模式相同的受门限双目观测；`assist` 也只退回到设定深度内
（默认 5 m）的双目观测，避免重新引入不可信远点。

输入可以是原始 LiDAR，也可以是课题一融合后的稠密点云，只要依然是标准
`sensor_msgs/msg/PointCloud2`、时间戳是原始传感器时间，且 `frame_id` 与所给外参一致。
两份项目接口文档没有锁定一个单独深度图话题，因此本次选择已有的
`/Car/T1/fusion/lidar/points` 作为通用几何输入，不新造课题一接口。

外参文件必须包含 `LiDAR_to_Cam_L.RT`，它实际表示“当前点云 `frame_id`
到未矫正左相机”的刚体变换。节点先将点云变换到矫正左相机坐标系，再进行：

- `direct`：整帧点云随关键帧位姿进入 `map`。相机视野内投影语义，视野外 360°
  几何仍保留且语义为 `unknown`；占据光线从实际点云传感器原点发出，可靠局部
  地面/非地面分别补充 free/occupied 终点，无法判断时不虚构证据。
- `assist`：建立投影 Z-buffer，在有界像素邻域内为双目特征查找最近表面深度，
  修正后的 3D 点仍在双目特征像素射线上，因此占据原点仍是左相机。它只生成相机视野内的
  稀疏关键帧地图点，不保留视野外 360°点云。

点云时间契约必须显式选择：

- `lidar_temporal_mode=none`：默认兼容模式，不修正点内畸变或点云/图像整帧时差；
- `upstream_deskewed`：输入已由 FAST-LIO2/驱动/课题一 deskew 到
  `PointCloud2.header.stamp`，本节点只用外部 LIO 将整帧变换到图像时刻。
  它故意忽略 `time`/`curvature` 等字段，不会对 FAST-LIO2 点云二次去畸变；
- `per_point`：读取显式配置的标量点时间，契约必须是
  `header.stamp + offset = 该点采集时刻`，再用外部 LIO 包围位姿做补偿。

后两种模式必须使用 `localization_mode=lio` 或 `vo_lio`。它们禁止位姿
nearest fallback；时间字段、位姿包围或外参不满足时拒绝建图观测，
不会默默改回未补偿点云。具体数学、性能和混合精度结果见
`accuracy_results/p1_3_lidar_temporal_20260815/`。

LiDAR 模式默认用该外参的逆旋转将 `map` 对齐到 LiDAR 传感器坐标系，因此要求该
frame 遵循 ROS REP-103 的 X 前、Y 左、Z 上约定。这样无需继续猜测相机俯角；若上游
LiDAR frame 不是车体水平坐标，必须先改成合规 frame，或设置
`lidar_align_map_to_sensor_frame:=false` 继续使用 `camera_pitch_deg`。

LIO 里程计不进入三图精确同步器，而是放入有界时间缓冲。图像时刻只在以下情况
接受位姿：最近样本时差不超过 `lio_max_time_offset_sec=0.15`，或者插值两端都
通过该门限。因此不会用一条跨越 LIO 中断的长插值伪装成有效轨迹。

FAST-LIO2 已使用原始 IMU，所以 GTSAM 融合层不再加入同一份原始 IMU 因子，避免
重复计数。RoMa 中原有 IMU 仅用于 PnP 旋转初值，不提供平移。

即使开启 LiDAR，所有输出话题名和消息类型都不变；LiDAR 几何体现在 GridMap、
OccupancyGrid、自定义地图及地图快照中。`map_points` 只是有上限的派生可视化样本：
`vo` 模式从 RoMa 全局稀疏点取样，`lio` / `vo_lio` 模式从已归档的地图关键帧观测取样。
后者会反映 `direct` 或 `assist` 选中的几何证据，但仍不是原始、360° 或完整
LiDAR 全局点云，下游不得将它当作正式建图证据。
`publish_map_pointcloud` 默认为 `true`，因此旧接收端的默认行为未改；
只有确认没有下游使用该调试点云时才建议关闭。

### 7.4 默认发布时机与完整性

- `Odometry` 仍在每个有效位姿帧发布，不受地图修订和调试开关影响。
- 默认 `publish_unchanged_map_outputs=false`：`fixed` 模式只在真实 `map_revision` 变化时完整发布地图；`rolling_window` 和 `full_tiles` 在修订号变化或窗口跨过一个格子时发布稠密窗口。
- 跳过的只是内容未变的重复构造/发布；关键帧观测、pending 事务、SQLite 存档和地图融合不会抽样或合并。
- OccupancyGrid、GridMap 和 `IncrementalSemanticMap` 始终是正式数值输出；`publish_layer_images` 和 `publish_map_pointcloud` 只能关闭派生调试产物。
- 地图 publisher 只在全部成功后才记录本次发布签名。转换或 DDS 失败时，下一个同步边界会重试，不会重复融合已提交观测。
- 地图 QoS 仍是 Transient Local。`fixed` / `rolling_window` 晚加入可取最新完整窗口；
  `full_tiles` 会检测新 DDS 端点并主动发送冻结完整重放，不需要用每帧几十 MB 地图当心跳。

如旧接收端确实把“每个位姿帧都收到一张相同地图”当作心跳，可临时兼容：

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  publish_unchanged_map_outputs:=true
```

更推荐课题四依据 Transient Local 的最新样本，或后续单独定义轻量状态心跳。

### 7.5 正式/嵌入式的调试输出建议

P2-15 在同一同步序列前 45 帧以 `vo` 模式做了四组单变量运行。关闭两组派生输出后，
地图原子提交后的发布尾段均值从 0.367 s/修订降到 0.046 s/修订；
其中分层图和 RoMa 调试点云的平均主效应分别约为 44.7 ms 和 276.1 ms/修订。
该 VO 实验中，调试点云还会因每次重取已积累的 RoMa 全局点而随运行时间增长；
这一具体增长曲线不直接外推到 `lio` / `vo_lio` 的归档观测取样路径。

嵌入式或正式跑数时建议显式关闭：

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  publish_layer_images:=false \
  publish_map_pointcloud:=false
```

使用数据集包装脚本时，将同样两个 `name:=value` 参数追加在命令末尾。
这只关闭 5 张可重新派生的显示 Image 和当前定位模式的派生可视化点样本；
`Odometry`/Path/TF/TUM、OccupancyGrid、9 层 GridMap、8 层
`IncrementalSemanticMap`、全局瓦片、原子快照和 SQLite 原始观测都仍保留。

为了不在课题四确认前改旧端默认行为，两个参数的默认值仍是 `true`。
若只需查看分层图，建议只开 `publish_layer_images`；
`publish_map_pointcloud` 建议仅在短时查看当前模式的已取样地图几何时开启。
完整数据、对账和 review 见
`accuracy_results/p2_15_debug_output_ab_20260815/`。

## 8. `IncrementalSemanticMap` 消息

公开 `.msg` 文件未修改，数组均为行主序：

```text
index = row * width + column
```

`origin` 是区域左下角，第 `row` 行对应 Y 增大方向，第 `column` 列对应 X 增大
方向。

| 字段 | 类型 | 含义 |
|---|---|---|
| `header` | `std_msgs/Header` | 传感器时间戳和 `map` 坐标系 |
| `update_id` | `uint32` | 当前进程内单调递增的发布序号 |
| `resolution` | `float32` | 分辨率，默认 0.1 m/cell |
| `width`, `height` | `uint32` | 本次矩形地图的列数和行数 |
| `origin` | `geometry_msgs/Pose` | 矩形左下角在 `header.frame_id` 中的位姿 |
| `occupancy` | `int8[]` | `-1` 未知，`0`–`100` 为占据概率百分数 |
| `semantic` | `uint8[]` | 每格语义类别 ID |
| `semantic_confidence` | `float32[]` | 主导类别票数/总票数，范围 `[0,1]` |
| `elevation` | `float32[]` | 每格 Z 高程均值，未观测为 `NaN` |
| `elevation_variance` | `float32[]` | 高程样本方差，未观测为 `NaN` |
| `height_range` | `float32[]` | 格内最大高程减最小高程 |
| `roughness` | `float32[]` | `sqrt(elevation_variance)` |
| `observation_count` | `uint32[]` | 本格接受的 3D 观测数 |
| `class_names` | `string[]` | ID 到语义名称的映射 |

所有格层数组长度必须等于 `width * height`。

### 8.1 语义类别

| ID | 名称 | 占据角色 |
|---:|---|---|
| 0 | `unknown` | 未知 |
| 1 | `traversable_ground` | 自由/可通行 |
| 2 | `shadow` | 仅语义证据，不作为终点占据类 |
| 3 | `bright_rock` | 占据 |
| 4 | `rough_obstacle` | 占据 |

### 8.2 `SemanticMapBatch` 伴随批次

旧地图载荷未改。只有 `full_tiles` 需同时订阅：

```text
/Car/T3/semantic/incremental_map  IncrementalSemanticMap
/Car/T3/semantic/map_batch       SemanticMapBatch
```

| 字段 | 含义 |
|---|---|
| `map_id` | 配置的地图名 |
| `session_id` | 每个 mapper 进程唯一，用于识别重启 |
| `map_revision` | 已提交的权威地图修订 |
| `batch_id` | 当前会话内递增；同一地图修订重放时也会增加 |
| `phase` | `PHASE_BEGIN` 或 `PHASE_COMPLETE` |
| `reset` | 在本会话首个成功完成的批次为 true |
| `full_snapshot` | 本批列出一张冻结全局图，而不是仅变化瓦片 |
| `tile_x/tile_y` | 全局瓦片键 |
| `tile_revision` | 单瓦片会话内单调修订 |
| `tile_cleared` | 该载荷为全 unknown 墓碑，用于删除旧瓦片 |
| `payload_update_id` | BEGIN 为空；COMPLETE 与瓦片数相同，一一指向旧载荷 |

单个批次的线上顺序为：

```text
BEGIN -> 完整瓦片载荷 1..N -> COMPLETE
```

但 DDS 不保证两个话题之间的到达顺序，接收端必须缓冲而不是在回调中直接改图：

1. 以 `(session_id,batch_id)` 建立暂存批次，用同一 `header.stamp + update_id`
   匹配旧载荷。
2. BEGIN 和中间载荷都不改已提交地图。
3. COMPLETE 元数据与 BEGIN 相同、所有 ID 到齐、八个图层长度都为
   `width*height` 后，才在一次临时图上应用并原子替换。
4. 新会话/reset 只在完整批次提交时清图；半包或超时保留上一张完整图。
5. 增量按瓦片整块替换，相同修订幂等，小于已提交 `tile_revision` 的载荷丢弃。
6. 冻结全图重放不得覆盖重放期间已到达的更高地图/瓦片修订。
7. 超时缺包可调用 `/Car/T3/mapping/replay_full_map` 请求新的冻结完整批次。

DDS Reliable 是传输保证，不是“课题四已应用”的应用层 ACK。如验收需要
后者，还需双方另定 ACK 消息。

## 9. 三种地图发布模式

| 模式 | `IncrementalSemanticMap` | GridMap 等稠密输出 | 用途 |
|---|---|---|---|
| `fixed` | 完整固定 60 m 地图 | 同一固定区域 | 默认，与原代码最一致 |
| `rolling_window` | 完整 60 m 滚动窗口 | 同一滚动区域 | 实时局部规划 |
| `full_tiles` | 每条为一个完整 256×256 变化瓦片 | 机器人附近 60 m 滚动窗口 | 全局地图拼接 |

### 9.1 `fixed`：当前默认

默认参数下：

- `width = 600`
- `height = 600`
- `resolution = 0.1`
- `origin = (-30, -30, 0)`
- 物理范围为 `X=[-30,30)` m、`Y=[-30,30)` m
- 机器人运动时 `origin` 不变

这是对现有课题四接收程序风险最低的模式。但该话题不会携带 60 m 之外的
全局内容；内部全局快照仍会保留这些数据。

### 9.2 `rolling_window`

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  incremental_publish_mode:=rolling_window \
  data_dir:=/path/to/calibration
```

消息仍然是完整 600×600 矩形，但 `origin` 会随机器人位置按栅格对齐后移动。
接收方必须按 `origin` 定位，不能假设始终为 `(-30,-30)`。

### 9.3 `full_tiles`

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  incremental_publish_mode:=full_tiles \
  data_dir:=/path/to/calibration
```

默认每块瓦片：

- 256×256 cell
- 0.1 m/cell
- 25.6 m × 25.6 m
- 每条消息是该区域的完整最新状态，不是原始点或融合权重差分

课题四应按 `origin + resolution + width/height` 定位并整块替换，不要重复执行语义、
高程或占据融合。`-1`、`NaN` 和零观测值也是权威状态，用于清除旧内容。

该模式必须按第 8.2 节同时消费 `SemanticMapBatch`，不得把中间某一条旧载荷
单独当成已提交全局图。新 DDS 载荷订阅端加入时，节点会从写时复制的冻结
快照中每 0.1 s 发一块，最后发 COMPLETE。重放可能让已连接的其他订阅者
收到重复瓦片，因此接收操作必须使用 `tile_revision` 幂等替换。

正常变化瓦片批次也使用同一流式路径，不再在产生地图修订的回调中
同步物化所有瓦片大数组。新修订在旧批次发送期间到达时，旧批次完成
不会误清除新版本的脏标记。

如需手动补发：

```bash
ros2 service call /Car/T3/mapping/replay_full_map \
  std_srvs/srv/Trigger '{}'
```

服务只在 `full_tiles` 下存在；无 `IncrementalSemanticMap` 订阅者时会返回失败。

## 11. 坐标系、时间戳和数组方向

- `map`：X 向前，Y 向左，Z 向上。
- 默认子坐标系：`car_stereo_left_optical_frame`。
- 纯视觉模式默认相机俯角：向下 30°，通过 `camera_pitch_deg` 设置。
- LiDAR 模式默认由标定旋转对齐 `map` 到 LiDAR frame，不使用猜测的相机俯角；可用
  `lidar_align_map_to_sensor_frame=false` 恢复原俯角转换。
- 默认 Z=0 为第一帧左相机光心，不是地面。
- 如需地面接近 Z=0，应将 `map_z_offset_m` 设为实测光心高度的合适符号偏移，
  并用实际数据检查高程范围。
- 所有定位和地图输出使用左图的传感器时间戳，回放速度不会修改它。
- `IncrementalSemanticMap` 与 `OccupancyGrid` 使用左下角原点和行主序数组。
- `GridMap` 按 `grid_map_msgs` 的矩阵布局发布，不应用自定义消息的行主序规则
  直接解析它。

## 12. 内部地图融合

- 默认分辨率：0.1 m。
- 默认内部瓦片：256×256，即 25.6 m × 25.6 m。
- 瓦片按需创建，全局地图不受对外 60 m 窗口限制。
- 语义使用累积投票，置信度为最高票数占比。
- 高程先使用中位数/MAD 拒绝格内离群点，再增量计算均值和方差。
- 占据使用 log-odds，并沿实际几何传感器原点到观测终点进行光线更新。
- 每次默认最多抽样 1200 条占据光线。
- 地图证据仅在 SLAM 关键帧创建时新增融合；其他有效帧仍会发布定位，但默认不重复构造内容未变的地图载荷。
- 后端或回环修正位姿后，已归档关键帧证据会构建独立候选地图，成功后原子
  替换当前地图。
- 局部修正通过关键帧↔瓦片正反索引只重放受影响区的全部贡献观测；
  索引异常、修正太大或局部成本不划算时自动完整重建。
- 候选图在单个后台 worker 中构建，构建期间上一张完整图仍可发布；
  手动保存和关机会等待正在构建的修正候选图。

### 12.1 准确性、完整性与长时内存

地图证据的准确性和完整性是存储优化的硬约束：

- 每个已提交关键帧的全部地图观测都保留，不按时间、距离或缓存大小丢帧。
- 相机点始终以 `float64` 存储；zlib 只做无损字节压缩，不降采样、
  不改成 `float32`。
- SQLite 事务完整提交一批观测后才替换在线地图；磁盘写入中任何
  一条失败都会回滚整批，pending 证据保留等待重试。
- 历史重建若缺少任一归档关键帧位姿，会拒绝候选图并继续保留上一版
  完整地图，不再跳过该帧后提交少证据地图。
- 所选几何源（双目/LiDAR）构建失败时会保留该关键帧同帧语义图重试；
  未解决前禁止发布新地图。重试缓存达到上限时进入显式 fail-stop，
  不会删除旧证据来换取“继续有输出”。
- `map_observation_cache_size` 只限制 RAM 中的最近观测数；被淘汰的
  观测仍在磁盘存档中。BA、回环或因子图的局部修正会精确重放
  受影响贡献者；全局修正或安全检查不通过时才完整重放。
- 上述 RAM 上限只针对 mapper 的地图观测，不代表整个 RoMa 进程内存有界。
  `t3_gridmap_v2_ws/third_party/RoMa/` 按既有行为冻结，本轮不改关键帧图像所有权或 VO 算法。
- GridMap、占据、语义、高程与 `IncrementalSemanticMap` 都不因缓存而抽样。
  `/Car/T3/mapping/map_points` 仍按原有 `pointcloud_max_points` 上限发布；
  这只是调试点云带宽限制，不是地图证据限制。

这一边界已用“内存完整重建 vs 关闭并重开磁盘存档后完整重建”逐数组
对比测试：高程计数/均值/方差、语义票数和占据 log-odds 完全相同。

### 12.2 纯 VO 失跟恢复后的地图准入

`localization_mode=vo` 默认开启地图准入门。它不改 RoMa，也不改
`/Car/T3/semantic/current_pose` 的发布路径，只决定成功跟踪帧的新关键帧
观测能否写入持久地图：

1. 首帧和从未失跟的正常路径保持旧行为。
2. 任一视觉失跟会关闭新地图观测准入。
3. 恢复帧必须同时通过内点数、内点比例和帧间位姿连续性，并连续
   达到指定帧数才重新开门。
4. 普通 PnP 恢复的大跳变不被接受；RoMa 明确报告 `relocalized`
   时可建立新的远程参考，但默认仍需 3 帧稳定证据，不会立即把该帧写图。
5. 被拒绝的关键帧属于主动精度保护，不会进入观测构建失败重试；
   已提交的旧地图和已 pending 的可信事务仍按原路径同步。

`lio` 和 `vo_lio` 使用外部/融合位姿建图，该纯视觉位姿门自动旁路，
避免黑暗或少纹理导致 RoMa 失跟时误停可信的 LIO 地图。

调参示例（数值是当前保守默认，必须再用实车长序列标定）：

```bash
ros2 launch t3_semantic_mapping mapper_only.launch.py \
  localization_mode:=vo \
  map_admission_enabled:=true \
  map_admission_min_recovery_inliers:=25 \
  map_admission_min_recovery_inlier_ratio:=0.25 \
  map_admission_stable_frames:=3 \
  map_admission_max_translation_step_m:=1.0 \
  map_admission_max_rotation_step_deg:=20.0
```

日志 `Visual keyframe map observation intentionally rejected` 表示位姿仍已发布，
但该关键帧没有入图；`Visual map admission reopened` 表示连续稳定检查
已通过。只建议在对照试验中设置 `map_admission_enabled:=false`，不应用关闭
保护来掩盖长期失跟。

数据集回放器还有三个完整性参数：联合 practice launch 默认
`lossless_playback=true`、`lossless_max_in_flight_frames=2`、
`processing_ack_timeout_sec=120.0`。单独运行 `dataset_sensor_publisher`
时 `lossless_playback` 仍默认为 `false`，保留旧的独立发布行为。回放器另有
`publish_imu=true`，默认仍加载并发布原始 IMU；两个 practice launch 将它映射到
mapper 的 `enable_imu`，只在显式关闭时一起跳过无消费者回放。

在当前约 10 Hz 的数据中，默认 `lidar_buffer_size=20` 只覆盖约 2 s。早期宽松策略的
完整序列测试在 mapper 出现队列延迟后，`direct` 曾跳过 24 个点云关键帧，`assist`
曾有 34 个关键帧走 5 m 近距回退；这些数字用于说明缓存风险，不代表当前允许丢帧。
当前固定版在 `lidar_fallback_to_stereo=false` 时会阻止不完整地图发布并等待重试；
需要连续输出时应显式开启双目回退。离线慢速回放可按最大滞后把缓存临时提高到
`100`～`200`；真实机器人若长期算得比传感器输入慢，应优化/拆分处理管线，不能只靠
无限增大缓存。`direct` 建议保持 `lidar_fallback_to_stereo=false`，避免点云中断后
几何覆盖退化为较稀疏的近距离双目；`assist` 则建议开启安全回退。

输入和输出话题名也都是 ROS 2 参数，可在 launch 参数文件中修改。如车辆切换为
腿式平台，应把默认 `/Car/...` 按项目约定整体改为 `/Leg/...`。

## 14. 地图与轨迹保存

运行时手动保存：

```bash
bash scripts/save_grid_map_now.sh
```

等价命令：

```bash
ros2 service call \
  /Car/T3/mapping/save_grid_map \
  std_srvs/srv/Trigger '{}'
```

输出目录：

```text
<output_dir>/trajectory_opencv.tum
<output_dir>/trajectory_map.tum
<output_dir>/dataset_playback_summary.json
<output_dir>/input_processing_summary.json
<output_dir>/grid_map_snapshot/map_index.yaml
<output_dir>/grid_map_snapshot/.versions/snapshot-*/map_index.yaml
<output_dir>/grid_map_snapshot/.versions/snapshot-*/tiles/tile_*.npz
<output_dir>/map_observation_archive/observations_<session_ns>.sqlite3
```

`dataset_playback_summary.json` 只在数据集联合 launch 中指定了输出路径时生成；
`input_processing_summary.json` 由 mapper 正常关闭时写入。前者记账发布/回执，
后者记账同步/终止结果，长回放必须联合检查。

从 P2-13 起，前者还会写入 `complete_input_consumption_scope` 和
`input_selection`。数量必须按下列顺序解读：

```text
raw_left/right_row_count
    -> shared_candidate_pair_count
    -> stereo_skew_eligible_pair_count
    -> selected_frame_count
```

`complete_input_consumption=true` 只表示最后的 `selected_frame_count`
已全部发布并获得 mapper 终止回执，不代表原始目录每一行都是可用双目对，
也不代表每个终态都有有效位姿。同时检查
`excluded_by_stereo_skew_count`、`excluded_by_max_frames_count`、
`terminal_outcomes` 和 `mapper_results`。目标序列
`2025-06-26-23-01-34` 就是 157 共享候选→34 时差合格→34 选中，
只能写“34/34 合格对完整消费”，不能写“157 帧完整 VO”。

`map_index.yaml` 记录分辨率、瓦片尺寸、坐标原点、类别、融合参数、瓦片索引和
清除标记。每个 `.npz` 保存可继续融合所需的占据、语义票数和高程统计量。
根 `grid_map_snapshot/map_index.yaml` 仍是对外稳定的唯一加载入口；
不要自行猜测最新的 `snapshot-*` 目录。

快照现在是版本化原子保存：

1. 先在 `.versions/.staging-*` 写入所有瓦片和内部索引；
2. 逐层检查元数据、字段、dtype、shape 和数组内容；
3. 只有全部通过后，才原子替换根 `map_index.yaml`。

任一瓦片写失败、校验失败或 Ctrl+C/SIGINT 打断时，上一份已提交根索引
和它引用的瓦片都不变。每次成功后保留“当前 + 紧邻上一版”；保存过程中
还需容纳一份 staging，因此长时部署要按最坏三份压缩快照预留短时磁盘空间。
强制断电/SIGKILL 可能留下隐藏 staging，下次保存会只清理本组件命名的临时项，
已提交地图仍可加载。

旧的 `grid_map_snapshot/tiles/` 格式仍可读。首次原子保存会保留该旧目录，
第二次成功保存后再清理。同一 `grid_map_snapshot` 目录只允许一个 mapper
作为权威写入者；多节点并行运行时必须使用不同 `output_dir`。

快照保存的是完整内部全局瓦片地图，与当前对外发布模式无关。底层类已具备
快照加载能力，但当前 ROS 2 节点尚未提供“启动时自动恢复快照”参数。
保存会多一次逐瓦片读回校验，只影响手动/关机保存；不会降采样、
删图层或改变正常建图与发布的计算路径。

SQLite 文件是当次运行的可重放原始地图证据，每次启动新建会话文件，
不会与上次关键帧 ID 混合。它随运行时长增长，长时部署必须监控
`output_dir` 可用空间并按运行会话归档；不应用“超上限删旧观测”的方式换取
固定磁盘用量，否则会破坏回环后的全量地图准确性。

### 17.3 常见问题

| 现象 | 优先检查 |
|---|---|
| mapper 显示 waiting，没有帧 | 看启动日志的实际话题/QoS/同步模式；10 s 诊断会给出三路发布者数量 |
| 三图都有计数但没回调 | 根据 `formed no new synchronized group` 中的最新纳秒时间戳查采集时间；确认后才调 slop |
| 日志拒绝左右目 skew | 双目采集偏差超过精度门限；先查硬件同步，不要只为了进回调放宽 |
| 数据集已播完但 mapper 没处理 | 先看两份 summary JSON；联合 launch 默认会等就绪并逐帧回执，若关闭 `lossless_playback` 则仍可出现启动竞态 |
| 无损回放比设置的 `playback_rate` 慢 | 查 `effective_playback_rate_x` 和 mapper 耗时；这表示正在按真实算力背压，不应通过抽帧掩盖 |
| summary 有回执但没有位姿 | 回执只表示回调终止；查 `terminal_outcomes` 中的跟踪失败/定位不可用/异常分类 |
| `Algorithm root missing` | `algorithm_root` 未指向包含 `roma_vo.py` 的目录 |
| 无 CUDA | 虚拟环境 PyTorch/CUDA 版本、`CUDA_VISIBLE_DEVICES`、显存 |
| GridMap 中大量 `NaN` | 未观测格的正常表示；再检查融合点数和坐标偏置 |
| `full_tiles` 下重复瓦片 | 新订阅者触发主动重放；按 `tile_revision` 幂等替换，不要再融合 |
| 收到 BEGIN 后一直没有 COMPLETE | 丢弃超时缓冲、保留上一张完整图，检查双话题 QoS 后调用 `replay_full_map` |
| `replay_full_map` 返回无订阅者 | 先启动 `IncrementalSemanticMap` + `SemanticMapBatch` 接收端，再调用服务 |
| 开启 LiDAR 后没有地图修订 | 严格完整性策略会在点云关键帧缺失时冻结新地图；检查点云话题、Best Effort QoS、`frame_id`、时间差和外参路径，或显式启用双目回退 |
| `assist` 提示支持点不足 | 先检查投影外参/时间戳；再按点云密度调像素半径或最少匹配数 |
| 日志显示 `unexpected frame_id` | 修改 `lidar_expected_frame_id` 前先确认该坐标系确由当前外参描述 |
| 数据集完整 LiDAR 回放积压 | 将 `lidar_publish_max_points` 设为 5000，并降低 `playback_rate` |
| 外部 LIO 启动时拒绝运行 | 不要直接绕过保护；核对 `T_lidar_child` 后再设 `lio_child_to_lidar_confirmed=true` |
| 日志显示 `frame mismatch` | 核对 `/Odometry.header.frame_id` / `child_frame_id`，不要只改预期帧名来掩盖坐标错误 |
| 日志显示 `no time-valid pose` | 检查 LIO 是否使用原始传感器时间、DDS QoS 和 `lio_max_time_offset_sec`；不建议盲目放大门限 |
| `vo_lio` 提示缺少 GTSAM | 在 ROS 对应 Python 中安装/验证 `gtsam` 和 `gtsam_unstable`；默认 VO 不需要它们 |
| 日志提示 observation archive 写入失败 | 检查 `output_dir` 权限和剩余磁盘；不要通过丢弃 pending 观测绕过 |
| 日志提示 `Refusing to publish an incomplete map` | 找到所列关键帧的点云/位姿/观测构建原因；上一版完整地图仍保留，问题解决前不要绕过 fail-stop |
| 日志提示后台 GridMap correction 失败 | 上一张完整图仍有效；检查存档、位姿和内存，下一帧/保存/关机边界会重试，不要删除依赖索引来强行提交 |
| 日志提示 `Visual keyframe map observation intentionally rejected` | 纯 VO 刚经历失跟，当前恢复内点、连续帧数或位姿连续性未达标；位姿仍发布，该关键帧不入图 |
| 位姿持续但地图话题不再每帧更新 | 默认的无重复发布行为；检查 `map_revision` 和 Transient Local 最新样本，不要误判为建图停止 |
| `Ctrl+C` 恰好打断快照压缩 | 上一份已提交 `map_index.yaml` 仍可完整加载；查看 `.versions` 时可能短暂见到隐藏 staging，下次保存会清理。如果这是首次保存，之前本就没有可回退版本，节点存活时重新调用保存服务 |

## 18. 当前已知限制

1. `fixed` 对外只展示固定 60 m 区域，虽然内部和快照会继续增长，但课题四
   无法仅靠该话题获取 60 m 外的内容。
2. `rolling_window` 和 `full_tiles` 需要接收方明确理解矩形区域的坐标与覆盖语义。
3. 旧 `IncrementalSemanticMap` 为保持兼容仍没有会话/reset；只有选用
   `full_tiles` 并同时消费 `SemanticMapBatch` 才具备完整批次语义。
4. `Odometry` 三种模式都输出速度，但直接 VO/LIO 是离散位姿差分，当前协方差仍是
   “后验未知”的保守大值；用于控制或再次融合前必须按实车数据标定。
5. 标准 Image/Imu 兼容输入已支持可配置 QoS 和 exact/approximate 同步，
   但课题一自定义融合消息与课题二 `SceneSemanticModel.msg` 仍缺可编译
   定义和正式 rosbag，薄适配器尚不能完成。
6. 局部后端/回环修正已只重建精确影响区并在后台构建；大范围修正、
   索引安全检查失败和历史迟到观测仍会完整重建，需在大图/Orin 验证 2 s 指标。
7. 当前持久化保留了可继续融合的内部统计量，最终是否满足 3 GB/km² 需在更长
   路线上实测，不应用少量帧结果代替验收。
8. `full_tiles` 中一块 256×256 的 8 层自定义消息在 CDR 开销前约 1.7 MB，
   正常变化批次和完整重放的定时调度上限都是 10 瓦片/s，实际还受图像回调/
   DDS 背压限制；长距离需在 Orin/实际网络上评估总时间和 DDS 带宽。
9. `lio` 和 `vo_lio` 已能校正/替代 RoMa 位姿，但仍依赖正确的 IMU–LiDAR–相机外参；
   外部 LIO 协方差尚未按完整 SE(3) 伴随矩阵变换，因此融合暂用配置噪声。
10. LiDAR 与语义图仍不是硬件同步；当前已能选真正最近帧并用外部 LIO
    对齐到图像时刻。`per_point` 只用外部位姿插值，不等价于高频 IMU deskew；
    高速实车仍必须优先 FAST-LIO2 上游去畸变并用独立真值验收。
11. 相机视野外的 LiDAR 点只有几何和占据证据，语义为 `unknown`；最终语义覆盖率

    完全无相机模式。`assist`、双目建图、`vo_lio` 或启用双目回退时仍需要 RoMa。
13. `fusion_backend=gtsam_gp` 仍只是默认 10 s 滑窗的局部融合且不包含 GNSS；

14. `assist` 只修正用于 2.5D 地图的稀疏关键帧深度，不修改 RoMa 的跟踪、PnP 或回环。

    typed-buffer 和调试点云优化后的 6 帧短段约为 0.42～0.46×。P2-14 的

    35 个超 2 s 帧全是地图修订帧，而无修订帧 P95 为 0.803 s。长序列中 RoMa/地图段占比为
    65.71%/33.49%。P2-16 短段将地图阶段总时间降低 37.1%，回调 P95/最大降到
    1.333/1.945 s，但真实倍率仍只有 0.492×，RoMa 占已分类回调 87.4%。真实传感器
    无法因 T3 慢而重发历史帧，标准
    `ros2 bag play` 也不使用该回执自动节流；必须在 Orin 上做持续频率 profile，
    并与课题一发布序号/计数对账。
    P2-18 的 6 帧 `lio + direct` 视觉旁路回调均值为 0.369 s、输入监视器有效倍率
    0.713×，但首次地图提交仍有 1.865 s 冷启动尖峰，单靠短段不能判断长期实时。
    P2-20 随后跑完最长同步序列 231/231 帧：mapper 回调均值/P95/最大为
    0.128/0.658/1.204 s，但数据集包装器因仍串行回放 23,923 条无消费者原始 IMU，
    联合倍率只有 0.504×。P2-21 让 practice 数据集的 IMU 回放跟随已有
    `enable_imu=false` 后，同序列仍为 231/231、47 次修订和 47 条/194,290 点
    逐字节相同的 SQLite 原始归档；联合倍率达到 1.164×，回调均值/P95/最大为
    0.109/0.568/0.994 s。该结果关闭的是本机 direct LIO 数据集包装链瓶颈；
    需要视觉的模式仍低于 1×，两者都还要在 Orin/Humble 实时输入上复验。
    `enable_imu=false` 只停止本项目 mapper/数据集 publisher 的原始 IMU 路径；
    独立 FAST-LIO2 仍必须按其算法要求订阅和使用原始 IMU。
18. 数据集的原始行数不等于可用双目对数。目标序列只有 34/157 对通过
    20 ms 曝光时差门限，并存在 50.312 s 合格输入空洞。该序列可用于验证拒绝、
    恢复和完整性账本，不能用于完整双目路线精度验收。

## 19. 当前推荐用法

- 不确定课题四实现时：使用默认 `fixed`。
- 只需机器人附近局部地图时：双方确认 `origin` 后使用 `rolling_window`。
- 需课题四拼成全局大地图时：将第 8.2/16 节的 `SemanticMapBatch`
  接收状态机纳入双方锁定接口后使用 `full_tiles`。
- 双目近距离测试或没有可靠 LiDAR 外参时：保持 `enable_lidar_mapping=false`。
- 保留原有行为时：使用默认 `localization_mode=vo fusion_backend=none`。
- 黑暗/重复纹理长时运行且已完成可靠外参标定时：优先试验
  `localization_mode=lio fusion_backend=none`，先将 LIO 本身调稳。
- LIO 同时直接用点云建图且不允许退回双目时：显式设置
  `enable_lidar_mapping=true lidar_mapping_mode=direct lidar_fallback_to_stereo=false`；
  该组合自动旁路 RoMa，并用 `keyframe_interval` 调整有效 LIO 位姿的取图节拍。
- 使用两个 practice launch 回放“已保存 LIO + direct 点云”且 mapper 确实不消费
  原始 IMU 时：同时显式设置 `enable_imu=false`，可避免数据集事件循环回放无消费者
  IMU。实时 FAST-LIO2 仍在独立进程中消费它自己的 IMU，不得照搬为“关闭 LIO IMU”。
- 只在 VO 和 LIO 的时间/坐标/噪声都有实测后，再启用
  `localization_mode=vo_lio fusion_backend=gtsam_gp`。
- 需要 360° 几何/占据覆盖时：试用
  `enable_lidar_mapping=true lidar_mapping_mode=direct`。
- 实时 FAST-LIO2 点云建图时：首选 `/cloud_registered_body`、对应
  `T_camera_body` 和 `lidar_temporal_mode=upstream_deskewed`，不二次 deskew。
- 只有原始标准 PointCloud2 且上游明确给出 header-relative 点时间时，
  才选 `per_point`；不得用低频保存轨迹的结果代替实车 IMU deskew 验收。
- 希望保留双目地图结构，但阻止不可信远点并用点云校正受支持深度时：试用
  `enable_lidar_mapping=true lidar_mapping_mode=assist lidar_fallback_to_stereo=true`。
- 两种点云模式都应先核对时间差、外参投影、高程方向和覆盖范围，再用于正式数据。
- 三图的上游采集时间戳一致时保持 `image_sync_mode=exact`；只在实测时差后开启 approximate。
- Reliability 应逐话题匹配发布端；不要用全部 Best Effort 掩盖未确认的正式接口。
- 数据集试验保持联合 launch 的 `lossless_playback=true`，每次联合检查
  `dataset_playback_summary.json` 和 `input_processing_summary.json`；不用调高
  `playback_rate` 后仅看发布日志的方式声称完整或实时。
- 正式/嵌入式运行显式设置
  `publish_layer_images=false publish_map_pointcloud=false`；这是只减派生可视化的无损减负，
  不是删地图层或丢观测。需要 RViz 调试时再分别显式打开。
- 另外必须检查 `input_selection`；双目时差超限时保留 20 ms 几何保护，
  换用硬件同步的 rosbag/实时输入，不用放宽到数百毫秒的方式凑“全帧”。
- 无论对外模式如何，建议保持 `save_on_shutdown=true`，并在长距离测试中定期调用
  `/Car/T3/mapping/save_grid_map`。
